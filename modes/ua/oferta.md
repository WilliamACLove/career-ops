# Режим: oferta — Повна оцінка A-G

Коли кандидат вставляє вакансію (текст або URL), ЗАВЖДИ видати 7 блоків (оцінка A-F + G легітимність):

## Крок 0 — Визначення архетипу

Класифікувати вакансію за одним з 6 юридичних архетипів (див. `_shared.md`). Якщо гібрид — вказати 2 найближчих. Це визначає:

- Які proof points пріоритизувати в блоці B
- Як переписати summary в блоці E
- Які історії STAR готувати в блоці F

## Крок 0.5 — Юридичні hard gates (pass/fail, ніколи не усереднюються мовчки)

Перед оцінюванням будь-чого — звірити вакансію з блоком `legal` у `config/profile.yml` кандидата. Це структурні фільтри, а не зважені фактори — провалений гейт має з'явитися **явно** у вимірі Red flags І у фінальній рекомендації. Ніколи не давати провалу гейту мовчки розчинитися в непоганому загальному балі.

1. **Кваліфікація / статус адвоката** — звірити юрисдикцію/вимогу вакансії з кваліфікацією кандидата. Застосувати драбину суворості:
   - **Юридичні фірми: суворо**, особливо для судової практики — представництво в суді зазвичай вимагає адвокатського статусу (свідоцтво + членство в НААУ). Відсутність такого статусу при явній вимозі — майже блокер, зазначити прямо.
   - **Inhouse: помірно** — штатний юрист часто може консультувати й частково представляти роботодавця без окремого адвокатського свідоцтва; трактувати як зауваження, не блокер, якщо вакансія прямо не вимагає протилежного.
   - **Державний сектор і legal tech: мінімально** — інша кваліфікаційна процедура (конкурс на держслужбу) або взагалі без вимоги адвокатського статусу.
   - Якщо не впевнені у точних межах вимоги для конкретного типу справи — сказати це прямо, а не вгадувати.
2. **Рівень досвіду / PQE-банд** — якщо вакансія вказує банд досвіду (наприклад, "3-5 років практики", "senior associate", "5+ PQE"), порівняти з досвідом кандидата. Вихід за межі банду в латеральній вакансії фірми — сильний негативний сигнал: рекомендувати не подаватися без конкретної причини; уточнити, що коригування рівня на ±1 рік іноді можливе на етапі офера, але не на скринінгу.
3. **Патентний повірений** — ролі патентного діловодства вимагають реєстрації як патентний повірений (окрема кваліфікація від адвокатури) плюс технічну освіту. Якщо JD цього прямо вимагає, а `legal.patent_bar` — false, це hard gate.
4. **Ризик конфлікту інтересів** — для senior/counsel/партнерських ролей зазначити, що будь-який офер залежить від проходження перевірки на конфлікт інтересів. Зазначити ризик — не оцінювати балом.

Подати результати гейтів як короткий pass/fail список на початку блоку B. Провалений гейт обмежує рекомендацію незалежно від того, наскільки добре збігається все інше.

## Блок B — Збіг з CV

Прочитати `cv.md`. Створити таблицю: кожна вимога JD → точні рядки CV.

**Адаптовано під архетип:**

- Юрист фірми — транзакційна практика → пріоритизувати перелік угод на потрібному рівні досвіду: типи угод, обсяги угод, ownership драфтингу, ведення спеціалізованих workstream
- Юрист фірми — судова практика та спори → пріоритизувати досвід виступів: судові засідання, підготовлені процесуальні документи, участь в арбітражі/судових процесах, сила письмового мовлення
- Inhouse-юрисконсульт (комерція/продукт/дані) → пріоритизувати обсяг договірної роботи (SaaS/MSA/DPA), крос-функціональний консалтинг, регуляторну широту, plain-language комунікацію з небізнес-юристами
- Комплаєнс та регуляторний напрямок → пріоритизувати названі режими (ПВК/ФТ, санкційний комплаєнс, GDPR/захист даних), взаємодію з регулятором, розслідування, ownership програми
- Державний сектор / громадський інтерес → пріоритизувати обсяг судової практики, досвід на процесах, підтверджену відданість суспільній місії (клініки, стажування, попередня PI-практика)
- Legal Tech / Легал-інженер → пріоритизувати поєднання практичної юридичної експертизи з продуктовою/AI-обізнаністю — побудовані playbook'и, автоматизовані процеси, legal-tech сайд-проєкти

Розділ **прогалин** зі стратегією закриття кожної:

1. Це hard blocker чи nice-to-have?
2. Чи може кандидат продемонструвати суміжний досвід?
3. Чи є портфоліо-проєкт, що закриває цю прогалину?
4. Конкретний план закриття (фраза для супровідного листа, швидкий проєкт тощо)

## Блок C — Рівень і стратегія

1. **Рівень у JD** (банд досвіду/PQE для фірм; титульна драбина Юрист → Старший юрист → Радник/Counsel → Партнер для фірм, або Юрисконсульт → Головний юрисконсульт → Керівник юридичного департаменту для inhouse) vs **природний рівень кандидата для цього архетипу**
2. **План "продати senior без обману"**: конкретні фрази, адаптовані під архетип, конкретні угоди/справи для акценту, як позиціонувати підготовку у фірмі, клерkship або досвід у регуляторі як перевагу
3. **План "якщо знизять рівень"**: для фірм — коригування рівня на ±1 рік договірне на етапі офера (іноді нижчий рівень дає більше часу до партнерства); для inhouse — спочатку боротися за титул/рівень (Старший юрисконсульт vs Юрисконсульт, заступник керівника vs старший юрисконсульт), а вже потім за суму — бо % бонусу та рівень опціонів прив'язані до титулу

## Блок D — Компенсація та попит

Використовувати WebSearch для:

- Актуальні зарплати за роллю з канонічних джерел за типом роботодавця:
  - **Юридичні фірми:** галузеві огляди й рейтинги («Юридична практика» / Ukrainian Legal Gazette), розділи зарплат robota.ua/work.ua, LinkedIn — трактувати як орієнтир, точні лockstep-шкали, як у BigLaw США, в Україні рідкість
  - **Inhouse:** розділи зарплат robota.ua/work.ua/LinkedIn; DOU.ua/djinni.co — лише якщо роботодавець tech-компанія
  - **Держсектор:** офіційні шкали посадових окладів держслужбовців (категорія посади), якщо доступні
  - **Legal tech / inhouse в IT:** DOU.ua/salaries, djinni.co/salaries
- Репутацію компанії щодо компенсації
- Тренд попиту на роль
- **Валюта**: уточнити USD чи UAH; для ФОП — net чи gross

**Мовчання щодо зарплати — норма для юридичних фірм в Україні.** Більшість вакансій фірм не публікують суму ("конкурентна зарплата" — стандартна фраза); це не є тривожним сигналом само по собі.

**Класифікація типу роботодавця (обов'язково):**

| Тип роботодавця                                        | Типова надійність даних про компенсацію | Сигнали                                                                                          |
| --------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| Провідна юридична фірма повного циклу                    | Середня-висока                            | Впізнавана назва, структурована драбина рівнів, участь у міжнародних рейтингах (напр., «Юридична практика») |
| Середня/регіональна/бутикова фірма                       | Середня                                   | Менш публічна структура оплати, дискреційні бонуси, "конкурентна зарплата"                          |
| Inhouse — публічна/зріла компанія                        | Середня-висока                            | Структуровані рівні, база + бонус, іноді опціони                                                    |
| Inhouse — стартап / growth-stage                          | Середня-низька                            | Опціонно-важка структура, можлива інфляція титулів, рівень і бонус договірні                        |
| Державний сектор / судова система                        | Висока (за шкалою), але нижче ринку фірм  | Опубліковані шкали посадових окладів, категорія посади                                              |
| Громадська організація / правозахисна сфера / безоплатна правнича допомога | Середня-висока                | Опубліковані бенди, зазвичай суттєво нижче фірмового рівня; грантове фінансування впливає на стабільність |
| Legal tech / суміжні з юриспруденцією ролі                | Середня                                   | Часто база + бонус/опціони, діапазони частіше публікуються                                          |
| Аутстафінг/аутсорсинг юридичних послуг ("проєктна робота") | Низька                                    | Погодинна оплата, агентство як формальний роботодавець, "проєктна робота"/"аутстафінг" у тексті     |
| Рекрутингове агентство (контингентне)                     | Низька-середня                            | Стороннє розміщення, діапазон може відображати бюджет клієнта, а не умови конкретного офера          |

Якщо тип роботодавця невідомий — позначити `Unknown` і за замовчуванням встановити консервативну надійність `Низька`.

Якщо бренд відрізняється від фактичного роботодавця (наприклад, роль "юрист" у відомому банку/компанії насправді розміщена аутстаф-агентством), класифікувати за фактичним роботодавцем, а бренд-зв'язок зазначити окремо.

## Блок G — Легітимність вакансії

Проаналізувати вакансію на предмет сигналів, що вказують, чи це реальна, активна пропозиція. Це допомагає кандидату пріоритизувати зусилля на можливостях, які з найбільшою ймовірністю приведуть до реального процесу найму.

**Етичний підхід:** Представляти спостереження, а не звинувачення. У кожного сигналу є легітимні пояснення. Кандидат сам вирішує, як їх зважити.

### Сигнали для аналізу (за порядком):

1. **Свіжість публікації** (зі знімка Playwright): дата публікації або "X днів тому"; стан кнопки Apply (активна/закрита/відсутня/редирект на загальну сторінку кар'єр).
2. **Якість опису**: чи названо конкретну практику, тип справ/угод, суд/регулятора; чи згадано розмір команди/департаменту та лінію підпорядкування (хто керівник юридичного департаменту/партнер практики); чи реалістичні вимоги (банд досвіду vs описана відповідальність); чи вказано зарплату (мовчання — норма для фірм в Україні); яка частка тексту специфічна для ролі, а не шаблонна; чи є внутрішні суперечності (напр., "молодший юрист" + відповідальність рівня партнера).
3. **Сигнали найму компанії**: пошук новин про скорочення/заморозку найму в компанії за останній рік; якщо знайдено — чи стосується того самого відділу.
4. **Виявлення повторних публікацій** (з `scan-history.tsv`): чи компанія + подібна назва ролі публікувалися раніше під іншим URL; скільки разів і за який період.
5. **Ринковий контекст ролі** (без додаткових запитів): чи це типова роль, яка зазвичай закривається за 4-6 тижнів; чи має сенс роль для бізнесу компанії; чи є рівень посади таким, що легітимно довше закривається (наприклад, GC/партнерський рівень).
6. **Специфічні для юридичного ринку сигнали**:
   - Розміщення через рекрутингове агентство без назви роботодавця ("конфіденційна компанія/фірма") — не автоматично фейк, але без назви роботодавця й банду досвіду зважати як "Обережно"; активний контакт з іменним рекрутером з конкретним мандатом — навпаки, позитивний сигнал.
   - Аутстафінг/проєктна юридична робота, подана як штатна вакансія "юрист" — реальна пропозиція, але не кар'єрний латеральний перехід; позначити окремо.
   - Та сама вакансія розміщена 3+ агентствами одночасно — роль реальна, але процес буде хаотичним; звірити `data/scan-history.tsv` і поле `via=` у трекері перед поданням через будь-який канал.
   - Прохання заплатити за "розміщення"/"реєстрацію"/"просування" резюме — ознака шахрайства, позначати "Підозріло".

### Формат виводу:

**Оцінка:** один із трьох рівнів — **Висока впевненість** / **Обережно** / **Підозріло**.

**Таблиця сигналів:** кожен спостережений сигнал з висновком і вагою (позитивний/нейтральний/тривожний).

**Контекстні примітки:** будь-які застереження (нішева роль, держсектор, evergreen-позиція тощо), що пояснюють потенційно тривожні сигнали.

### Особливі випадки:

- **Держсектор/академічні вакансії:** довші терміни — норма (60-90 днів — нормально).
- **Evergreen/постійний набір:** якщо JD прямо каже "постійний набір"/"ongoing" — зазначити як контекст, це не ghost-вакансія.
- **Нішеві/executive ролі:** GC, партнерський рівень або вузькоспеціалізовані ролі (напр., структурування фондів, вузька IP-практика) легітимно залишаються відкритими місяцями.
- **Немає даних про дату:** якщо вік публікації невідомий і немає інших тривожних сигналів — за замовчуванням "Обережно" з приміткою про обмежені дані. НІКОЛИ не ставити "Підозріло" без доказів.
- **Через рекрутера (без публічної вакансії):** сигнали свіжості недоступні. Активний контакт рекрутера — сам по собі позитивний сигнал легітимності.

## Пост-оцінка

**ЗАВЖДИ** після генерації блоків A-G:

### 1. Зберегти звіт .md

Зберегти повну оцінку в `reports/{###}-{company-slug}-{YYYY-MM-DD}.md`.

- `{###}` = наступний порядковий номер (3 цифри, zero-padded). Щоб виділити цей номер атомарно та уникнути станів гонки, ви ПОВИННІ виконати `node reserve-report-num.mjs` для резервування номера (stdout поверне `{###}`), записати звіт, а потім виконати `node reserve-report-num.mjs --release {###}` для звільнення маркера (sentinel).
- `{company-slug}` = назва компанії: lowercase, пробіли замінити на `-`, прибрати спецсимволи (наприклад, `Acme Corp` → `acme-corp`)
- `{YYYY-MM-DD}` = поточна дата
- **Вакансія через агентство з невідомим кінцевим роботодавцем:** slug — `confidential-{agency-slug}` (напр., `042-confidential-hays-2026-07-06.md`). Файл НІКОЛИ не перейменовується після розкриття роботодавця — оновлюється лише заголовок/шапка.

**Формат звіту:**

```markdown
# Оцінка: {Компанія} — {Роль}

**Дата:** {YYYY-MM-DD}
**URL:** {посилання на вакансію}
**Via:** {агентство/рекрутер, або "—" для прямої заявки}
**Архетип:** {визначений}
**Бал:** {X/5}
**Легітимність:** {tier}
**PDF:** {шлях або "очікується"}

## A) Резюме ролі

(повний вміст блоку A)

## B) Збіг з CV

(повний вміст блоку B, включно з таблицею hard gates)

## C) Рівень і стратегія

(повний вміст блоку C)

## D) Компенсація та попит

(повний вміст блоку D)

## E) План персоналізації
```

### 2. Зареєструвати в трекері

Для **нового** запису не редагувати `data/applications.md` напряму. Замість цього записати один TSV-рядок у `batch/tracker-additions/{num}-{company-slug}.tsv` з 8 або 9 колонками через табуляцію:

```
{num}\t{date}\t{company}\t{role}\t{status}\t{score}\t{pdf_emoji}\t[{num}](reports/{num}-{slug}-{date}.md)\t{note}
```

- `{num}` = наступний порядковий номер (ціле число, обчислити з `reports/`)
- `{status}` = `Evaluated`
- `{score}` = формат `X.X/5` (наприклад, `4.2/5`)
- `{pdf_emoji}` = `✅` або `❌`
- `{note}` = короткий коментар (опціонально, колонку можна опустити)

**Поле Via (якщо вакансія через агентство/рекрутера):** додати як окреме тегіроване поле `via={Агентство}` після notes (див. AGENTS.md для повного формату TSV) — ніколи не як позиційне поле без тега.

Потім виконати `node merge-tracker.mjs` для злиття в `data/applications.md`.

Для **існуючого** запису — оновлення статусу/нотаток проводити через канонічний CLI: `node set-status.mjs <report#|company> <State> [--note]` (не редагувати таблицю вручну).
